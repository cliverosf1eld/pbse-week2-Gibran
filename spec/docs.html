Conventions

All monetary amounts are integers in the minor unit of the stated currency; the currency is carried explicitly beside every amount. All timestamps are RFC 3339 with an explicit UTC offset, for example 2026-03-04T12:10:04+07:00.

Clients MUST ignore unknown response fields. Clients MUST treat an unrecognised enumeration value as the nearest non-terminal state and MUST NOT crash on it. These two sentences are what make every additive change to this interface legal.

Idempotency

The Idempotency-Key header is required for booking requests, and its value must be a version-4 UUID with hyphens. It’s required on POST /v1/bookings, because creating a badminton court booking is a consequential operation that must not happen twice. Keys are kept for 24 hours. A key reused after that period is treated as new. The server returns 409 Conflict with the problem type https://api.example.com/problems/idempotency-key-reuse.

Bookings

Create a badminton court booking

Creates a badminton court booking.

This is a consequential operation: the same booking intent MUST NOT create multiple bookings when the client retries the request. Clients MUST generate an Idempotency-Key when the user confirms the booking and MUST reuse the same key for retries of that intent.

header Parameters
Idempotency-Key
required
string <uuid>
Example: 0f7c1b9e-3d21-4a6f-9c05-8e2b7d41a9f0

Generated by the client at the moment the user confirms the action, and reused unchanged for every retry of that same intent. Retained 24 hours. Reuse with a different body returns 409 idempotency-key-reuse.

Request Body schema: application/json
required
courtId

string^crt_[A-Za-z0-9]{3,}$
